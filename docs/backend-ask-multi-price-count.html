The multi-price receipt count

Finding D from the 23 Oct re-check. Three numbers on a query that already reads exactly the right rows. Without them the Package deal pattern cannot fire at all, and it has not fired since the receipt walk was deleted on 22 Oct.

Endpoint: POST /cashiers/price_points No new table, no new index, no extra read of sales_partitioned

What it is for

Package deal is the pattern where the same receipt rings the item at two different prices — a BOGO, or a 2-for where one unit rings full and the other discounted. It is the one pricing pattern that cannot be seen in a price list, because the signal is not which prices exist but which ones land in one basket together.

The browser used to get it by downloading every receipt for the item and checking each one. That walk was deleted when price_points took over — rightly: it was slow, capped at 400 receipts, and priced weighed items wrong. But the count went with it, and the pattern has been judged without it ever since, so Package deal never fires.

Nothing else is missing. Every other pattern — Multi-buy, volatility, the stable cases — already reads what the endpoint returns today.

The three numbers

multi_price_receipts
Receipts on which the item rang at more than one price.
receipts_total
Distinct receipts the item appeared on at all. The denominator.
max_price_spread
The widest max − min inside a single multi-price receipt. Used in the sentence the panel prints, not in the decision.

receipts_total cannot be worked out from the rows you already return. Summing receipts across the price points double-counts precisely the receipts this feature is about: a receipt that bought the item at two prices is counted once in each of those two rows. That is why the denominator has to come from the server as well, rather than being added up in the browser.

What the browser does with them, so the definitions are pinned to a use:

// fires when at least 30% of receipts carry more than one price
mixedPct = multi_price_receipts / receipts_total * 100
→ "47% of receipts ring this item at more than one price, spread up to $1.50."

Prices compare by amount, not by price type. REG $3.34 and SALE $3.34 are one price here — the customer paid the same money twice, which is not a package deal.

The change

The line and sold CTEs are untouched. unit_price moves out of the final select into a CTE of its own, so the existing output and the new count share one definition of a price rather than carrying two copies that can drift.

priced as (
    select
        receipt,
        coalesce(nullif(trim(price_type), ''), 'REG') as price_type,
        (not weighed and qty > 1) as multi,
        -- Unchanged. Lifted out of the final select so both outputs below
        -- share one definition of "a price" and cannot drift apart.
        case
            when lbs > 0 and coalesce(price, 0) > 0
                 and abs(net - price * lbs) <= price * 0.005 + 0.005
                then round(price::numeric, 2)
            else round((net / case when lbs > 0 then lbs else qty end)::numeric, 2)
        end as unit_price,
        day, qty, lbs, net, weighed
    from sold
)

The existing output then reads it instead of recomputing it. Same rows, same order — price_points in the response does not change:

-- The existing output, now reading unit_price instead of recomputing it.
select
    price_type,
    multi,
    unit_price,
    count(distinct receipt)::int         as receipts,
    sum(qty)::float8                     as units,
    round(sum(lbs)::numeric, 3)::float8  as weight,
    round(sum(net)::numeric, 2)::float8  as sales,
    count(distinct day)::int             as days_seen,
    max(day)                             as last_seen,
    bool_or(weighed)                     as weighed
from priced
group by price_type, multi, unit_price
order by receipts desc, unit_price desc

And the new aggregate:

-- The new one. Same CTEs, one more pass over a set already in memory.
per_receipt as (
    select receipt,
           count(distinct unit_price)        as prices,
           max(unit_price) - min(unit_price) as spread,
           bool_or(weighed)                  as weighed
      from priced
     group by receipt
)
select
    count(*)::int                            as receipts_total,
    count(*) filter (where prices > 1)::int  as multi_price_receipts,
    coalesce(max(spread) filter (where prices > 1), 0)::float8
                                             as max_price_spread,
    bool_or(weighed)                         as weighed
from per_receipt

Two statements or one — your call. If two, the line / sold / priced text is worth hoisting into a single module-level string, so there is one definition of a price in the file rather than two that have to be edited together.

The weighed-item trap

This is the part worth deciding before anything is written, because the obvious implementation is wrong on scale items.

Two packs of chicken in one basket will usually compute to two different prices per pound, for the reason already documented in that query: the total is rounded to the cent and the weight to the hundredth of a pound before either reaches us. The shelf-price clamp collapses that when the line is within what the rounding can explain — but a line outside it reports what was paid, and two such lines make the receipt look mixed when nothing was discounted.

And a package deal on a scale item is not a real pattern. A BOGO is rung on packages, not on pounds.

A
Recommended. Return multi_price_receipts and max_price_spread as null when the item is weighed. One rule, in one place, and nothing downstream can misread the number because there is no number to misread. receipts_total stays a real count — it is right either way and useful on its own.
B
Return them always, and the browser suppresses Package deal when weighed is true. Works, but then the rule lives on our side of the wire while the trap lives on yours.

Either is fine — say which and the frontend will match it. If nothing is said we will build for A.

Response shape

{
  "error": 0,
  "success": true,
  "count": 3,
  "price_points": [ ... unchanged ... ],

  "receipts_total":       84,    // distinct receipts the item appeared on
  "multi_price_receipts": 39,    // of those, how many carried two or more prices
  "max_price_spread":     1.50   // widest gap inside one such receipt
}

Three new top-level fields beside price_points, which is unchanged. The browser will treat all three as optional, so a dev deploy where the API is still the old one keeps rendering exactly as it does today — Package deal simply stays quiet, which is the current behaviour anyway. Nothing has to ship in a particular order.

What it costs

Nothing meaningful. The same lines are already selected, filtered and materialised for the output that exists; this is one more aggregate over that set. No new table, no new index, no second read of sales_partitioned, and the expensive part of the endpoint — the partitioned scan on storeid, date and product code — is untouched.

How we will check it

  1. COKE 6PK .5LT (4900002468), storeid 695 (#361), 10/14–10/20. It rings 84 transactions across three prices — $3.34 SALE, $4.00 STOR, $6.49 REG. Any basket holding the sale price and one of the others should land in multi_price_receipts.
  2. A single-price item over the same week returns multi_price_receipts 0, and the panel’s pattern note stays off rather than reading “0% of receipts”.
  3. Fam Pak Breast Tenders (20016900000), same store — weighed, so under option A both counts come back null and Package deal is never offered for it.
  4. receipts_total is less than or equal to the sum of receipts across the price points, and strictly less whenever multi_price_receipts is above zero. That one inequality is the whole bug this fixes.
