Why the name is what vanishes

Three nested widths decide how much room the name gets, and only the last of them is flexible:

  • The report panel is 52% of the content area (SalesLedger.tsx).
  • The signal list inside it is 39.5% of the panel (PopupSubDeptList.tsx). So the sub-department rows live in roughly a fifth of the window.
  • Inside the row, the numbers are fixed: TY at 64 px, the two comparison pills at PCT_COL_W = 72 px each (src/utils/severity.ts:22), two 14 px gaps and a 10 px lead. About 246 px that cannot shrink.

The name cell is the only item in the row with flex-1 and min-w-0. The number group has no min-w-0 and children marked flex-shrink-0, so its minimum size is its content, and it holds. CSS therefore has exactly one place to take the missing pixels from.

246 px of fixed column inside a fifth of the window needs roughly 1,200 px of content area before the name gets its first pixel — which is the threshold the run measured, from the other side.

  className="text-[12px] font-medium text-content truncate flex-1"
>
  {r.desc}
</span>

What changed

Three things, so no single one has to carry it:

  1. A floor on the name cell, so it is no longer the only column that yields. A window too narrow for the row now clips its right edge, which a reader can recover from by widening the window. A blank name column is not recoverable — nothing on screen tells you what you are missing.
  2. A floor on the signal list, so it is no longer a pure percentage of a percentage and the detail side of the drill gives ground first.
  3. vs LY hides under 1200 px, on a named breakpoint set at the threshold the run measured. It is the weaker of the two comparisons, and on a store with no history on file — like the 695 this was found on — it is a dash on every row anyway.

How to check it

  1. Sales › store 361 › click the row, Sub dept tab, as before.
  2. Narrow to 1024, 1080, 1120, 1160. Expect 0 names hidden at every width, against 27, 27, 27 and 26 before.
  3. Below 1200 px the vs LY column should be absent — header and cells together, no half-aligned row.
  4. At 1200 and above, all three number columns return.

Where else the pattern sits

The same truncate flex-1 name against fixed number columns appears in PopupHourlyView.tsx:609, CategoryDetailPanel.tsx:529 and LPStorePanel.tsx:374. We left those alone: only the sub-department list actually breaks, because it is the one pairing long labels with a narrow panel, and a floor on a column that was never squeezed is a change with no evidence behind it. Worth a look in the next run — narrow the Categories and Loss Prevention panels and see whether anything there gives way too.

13 MB in five pages for one store-week

Confirmed Accurate, and it is already the reduced shape. What is left needs the server.
Files
src/pages/vendors/prod/vendorsData.ts, src/pages/subDepts/prod/SubDeptMargins.tsx:67–114, shared paging in src/utils/marginRows.ts
Verdict
Real. One frontend win available now; the rest is a backend ask.

Context the numbers deserve

The two-request shape the run measured is the result of an earlier pass at exactly this problem. It used to be subs/sub_sales to learn which departments exist, then subs/subs once per department per period — 1 + (departments × 3) paginated calls, all firing at once, which made Vendors the most expensive page in the app to open. Two changes removed that: sub_department: 0 asks for every department in one read, and because last week is this week shifted seven days, one contiguous 14-day range covers both.

So 13 MB is what is left after the obvious reduction. The payload is large because these are item-level pages: the drill-down, the day grid, the price points and the cost analysis all read individual lines. "Return one small payload per window" on its own would take those features with it.

The one thing we can fix without the server — and why it is not in this batch

Sub Dept Margins and Vendors send identical bodies and build different views from the same rows; your own measurement proves it. There is no cache between them, so opening one and then the other downloads 13 MB twice. A cache keyed on the request arguments inside src/utils/marginRows.ts would fix that in one file for every page that reads item rows — Vendors, Sales' sub-dept drill, Item Report, Inventory and the item-performance panels all go through it.

Deliberately not shipped with the other four. Caching paged reads means deciding when they go stale, and the failure mode of getting that wrong is showing somebody last week's numbers under this week's dates — quieter and worse than the problem it solves. It wants its own pass, not a tail-end-of-the-day one. The four fixes above are all deletions, floors and arithmetic; this is the one with a way to be subtly wrong.

Smaller note for whoever takes it: SubDeptMargins.tsx carries its own copy of the paging loop rather than using the shared helper, so it would miss the cache. That copy should go first.

What we would ask the server for

Not a replacement for subs/subs — a companion to it. One aggregate read per window, grouped by sub department and by vendor, carrying net, COGS, units and weight. That lands the page, grades the list and draws the header off a payload in the kilobytes. Line rows then load on a drill, for the one department or vendor someone actually opened, which is a hundredth of the data for the same screen.

Until that exists, a group search on these pages multiplies the download by the number of stores, which is the 60-store failure in the 11 Sep report. We would not call the current shape safe for groups.

Both pickers read the same array

There is one store fetch in the app, on sign-in, and it populates one slice. Every picker on both lists reads user.assignedStores from it. The app has no mechanism by which one page could be scoped differently from another — so the draft's two candidate causes ("the 7-store picker is not filtered to assigned stores, or the assignment is wrong") cannot be what is happening.

What differs is the control. SearchStore is a typeahead, and its input holds the restored store's name after sign-in. That name is then applied as a filter over the list:

SearchStore.tsx:46 — the selected store's own name, used as a query
useEffect(() => {
  // no query: show everything
  if (!context.selectedStore || (!query.length && context.selectedStore)) {
    setFilteredStores(context.assignedStores);
  } else if (context.selectedStore && query.length > 0) {
    // query is "Bruces Foodland 361" -> exactly one match
    const filtered = context.assignedStores.filter((store) =>
      store.store_name.toLowerCase().includes(query.toLowerCase())
    );
    setFilteredStores(filtered);
  }
}, [query]);

So on a page the user lands on with a store already restored, the list rendered into the DOM holds one row: the store whose name is sitting in the box. Clicking the box clears the query (SearchStore.tsx:70) and all seven come back. The draft says the lists were "read from the picker's own data on the page", which is consistent with reading a closed typeahead whose query had not been cleared yet.

Thirty-second check for the next run: open Sales, click into the Store box, and count. We expect seven.

The draft's own evidence names the cause. The two testids it recorded are two different components, and the page lists line up with them exactly:

The real finding, which survives

Strip the rendering away and a genuine question is left, and it is the more important one: assigned_stores returns seven stores for an account set up for one. Both pickers show seven because the backend says seven. That is not a display bug, and it is worth a separate ticket.

Sales and Categories disagree on last week because they are not comparing the same thing

Not a defect Both figures are right. The implied $93.7K is a denominator neither page used.
Sales
src/pages/sales/prod/shared/ledgerUtils.ts:314–350 — day-matched at store level
Categories
src/pages/categories/prod/categoriesUtils.ts:168–190 — paired per category, per day
Verdict
Two defensible comparisons. The fix is to say which is on screen.

The two comparisons

Sales compares the store's week against the store's last week, matching day for day. A store that traded all seven days in both weeks gets the plain figure: $100.4K against $90.3K is +11.23%, and the page prints the $90.3K because it is a real total.

Categories pairs at a finer grain. For each category, each day is matched to the same weekday last week, and a category-day with no last-week row is dropped from both sides — comment at categoriesUtils.ts:105–109, the arithmetic at :168–190. The percentage is therefore twNetForLW against lwNet, and twNetForLW is not the $100.4K in the header. A category that sold this week and did not exist last week contributes to the header and to neither side of the comparison.

The numbers agree once you use the right denominator

Back-solving $100.4K ÷ 1.0715 = $93.7K assumes Categories compared against the full week. It did not. Run it the other way instead, with Sales' $90.3K as the last-week total:

StepFigure
Last week, as both pages hold it$90.3K
× Categories' +7.15%$96.8K
This week inside paired category-days$96.8K of the $100.4K
This week in category-days with no last-week matchabout $3.6K

About $3.6K of this week sits in categories that had nothing last week — which is the same order as the $2,910.71 in 15 uncategorised buckets the run noted, and in the same direction. Nothing here needs tying out against the store report: the two pages are consistent, and the discrepancy is in the back-calculation.

What we are not changing, and the one thing we are

The arithmetic stands. Keeping the paired form is deliberate: counting a category that did not exist last week as a fall to zero would turn every new line in the store into a loss.

What is wrong is that the Categories header shows a percentage whose base is invisible, which is what let a careful reader derive a last-week total the page never used. Printing the comparison base on that header — the way the Sales page prints its "LW $90.3K" — is a wording decision rather than a code one, so it is sitting with Steve rather than shipped with the other four. It is the only item on this list we have left open deliberately.

One line apart

The draft is exactly right that both screens receive the same data and differ in the browser. Here is the difference, side by side:

MarginPerfLeftPanel.tsx:157 — unweighted mean of department percentages
const avgMarginPct = grades.length
  ? grades.reduce((acc, g) => acc + g.grade.tyMarginPct, 0) / grades.length
  : null;
VendorListPanel.tsx:219 — dollars over dollars
// Store margin is WEIGHTED -- dollars over dollars, not a mean of the
// vendors' percentages, which would let a $5 supplier count as much as
// the wholesaler behind half the shelves.
tw: isMargin ? marginPct(twNet, twCogs) : twNet,

Sub Dept Margins gives floral the same vote as grocery. A handful of small, high-margin departments pull the figure up, which is exactly the 4.87 points between the two screens and the direction of it. The same mistake is in the delta: avgLwDelta averages each department's point move rather than weighting it, which is where −5.29 and −5.39 come from.

The dev tree has had one pass at this already — it now averages only over departments that have a comparison, so a department with no last week stopped contributing a zero. The weighting itself was not addressed, in either tree.

What changed

The dollars behind the rate were being thrown away after the division. They now come out of the day-matching as a MarginDollars figure on every department's grade, so the store margin sums net, sums COGS, and divides once.

  • Every department in the week is graded, so that sum is the store's whole net and COGS — the same totals Vendors reaches by grouping the same rows by supplier. The two headline margins now match to the cent.
  • Both points deltas are weighted the same way, each side scoped to the days it matched. Where a side has no sales they read as a dash rather than 0.00, which claimed the margin had held flat.
  • marginPct had three private copies and now has one, in utils/grading. Two implementations of a four-line function is the shape that let the screens drift in the first place.
  • The rule moved out of the component into the page helpers, so it is under test rather than buried in a render.

How to check it — and a check worth keeping

  1. Load Sub Dept Margins and Vendors for store 361, week ending 10/20/2026, in margin mode.
  2. The two header margins should now be the same number. Expect about 27.04% on both, where Sub Dept Margins said 31.91%.
  3. This is worth a permanent assertion in the harness: both screens are built from one endpoint, so any future disagreement between those two headers is a bug by definition and needs no judgement call to spot.

The number on screen drops. 31.91% to about 27.04% on that store-week, and similarly elsewhere. It will read as a regression to anyone watching the header, so it is going in the release notes as what it is: the margin was overstated, and this is the store's real one.

What was happening

A handful of storeids cover two physical stores. Every single-store page fetches by storeid, so those responses come back with both locations added together, and each page has to split them. Four pages do. Vendors and Categories did not.

So on 685, every vendor figure and every category figure was two stores at once — sales, COGS, margin, the day strip, the item drill. Nothing on screen said so, and no total looked impossible. It is the same shape as the sales/topitems problem we already have an ask in for, except this one was fixable in the browser.

Worth being plain about why this was not in your report: nobody had opened 369. Your run stayed on 695 / #361, which is an ordinary single-location store, so every number it saw was right. This is the bug your next run would have found.

What changed

Both pages now do what their siblings do: take the locations from the rows, land on the first one rather than the combined view, and offer the same LocationTabs switcher. The raw rows stay whole, so switching location re-presents what is already loaded rather than asking for the same paginated read again. The header names the location you are on — storeName resolves by storeid, so it would otherwise keep naming the other store while every figure moved.

Categories narrows its per-category drills too: items and hourly are also fetched by storeid, and without that the right-hand panel would describe a different store from the row that was clicked.

The quieter half, which was in a page you did test

Writing the test for Vendors turned up a second defect, in Sub Dept Margins — one of the pages that was supposedly already correct.

The scoping helper, scopeToStoreNumber, leaves an array alone when it holds fewer than two store numbers. That is the right answer to "does this response need splitting at all". It is the wrong answer to "which location is the reader looking at" — and a co-located store can easily have a period only one of its locations traded in. A last year that 370 has no history for and 369 does. In that case the guard handed 369's rows to somebody sitting on the 370 tab, and reported it as that location's last year.

There is now a strict variant beside it, onlyStoreNumber, documented against its sibling so the next person picks deliberately. Sub Dept Margins moves to it.

How to check it

  1. Open Vendors on store 369 (storeid 685), any week. Expect a 369 / 370 / Both tab strip above the filter row, and the header to read 369.
  2. Switch to 370. Every figure should change, the header should say 370, and no new request should go out — it is a rebuild.
  3. Both should give you the combined figures the page used to show unprompted.
  4. Repeat on Categories. See the note below if the tabs do not appear.
  5. On Sub Dept Margins for the same store, check a period only one location traded in — a last year with history on one side only. The location without it should read as no comparison, not as the other location's number.
  6. On an ordinary store like 361, nothing should change anywhere: the tabs render nothing below two locations.

One thing we cannot check from here. Whether Categories shows the tabs at all depends on cat_sales returning a per-location store_number. The type declares the column, but a declared field is not a populated one. If every row carries the same number, the tabs render nothing and the page behaves exactly as it does today — so the change is inert until the rows support it, and correct the moment they do. Step 4 above is the test: if Categories shows no tabs on 369 while Vendors does, that is the endpoint, and it becomes a sixth backend ask.

On the harness: the DOM is not the screen

One change, three findings

Three of this run's findings turn on the same distinction, and the run landed on both sides of it:

FindingIn the DOMOn screenVerdict
Issue 1 — sub-dept namesYesNoReal bug, correctly caught
Issue 4 — one-store pickerOne rowSeven, once openedFalse positive

Issue 1 is the valuable half. It was caught because the run measured rendered width and screenshotted it, which is the only way that bug is findable — the text is all there in the markup, and a reader cannot see a word of it.

The other two came from reading markup as though it were the page. We have fixed the Receivers one at the source — a hidden control is worth removing whoever is reading it — but the picker is not a bug, and the next run will meet more of these. Both would have been filtered out by one rule:

Suggested rule: before reporting what an element contains, check that it is painted — a non-zero client rect, and no display:none, visibility:hidden or zero-size ancestor. Then report "in the DOM, not visible" as a finding type of its own rather than as absence or presence. Had that category existed, issue 1 would have been found the same way and the two false positives would have been found as what they are: markup we should clean up, not behaviour a user can see.

A second thing that would raise the signal: for a typeahead, open it before reading its list. A closed one shows the filter, not the options — which is the whole of issue 4.
