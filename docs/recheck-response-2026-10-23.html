AU

Sub Dept Margins and Vendors differ by 0.03 pts on last week

Fixed 81fa1f3e Not by re-weighting

You are right that the rule should hold, and the headline figure does — both read 27.04% because that is a whole-period number. The delta cannot agree, and weighting is not why.

Each page day-matches at its own grouping. Vendors drops a day from the comparison when that vendor did not trade in both weeks; Sub Dept Margins drops it when that department did not. A Tuesday a vendor missed is still a Tuesday its department worked, so the two sums cover slightly different sets of rows. Same data, same arithmetic, 0.03 pts apart.

So the fix is not to re-weight anything. The store header delta should day-match at store level on both pages, which makes them equal by construction rather than by coincidence. Each row keeps its own matched days, because for a single vendor or a single department that is the correct comparison.

Done. Both store header deltas come from store-level matched days, in one shared helper. The two headers now agree on every figure, not only the margin. The sales delta is untouched — it is a total rather than a rate, so the grouping never changed it.

What is still open

P

Which unit the cost is in, on a random-weight pack

Needs one look at the rows With O

Steve has settled the source: the cost on a sales row is what the item cost at the moment it rang, so nothing is wrong with where it comes from. What is left is narrower and answerable from data.

There are two kinds of weighed item and they do not cost the same way. A true scale item — bananas — has a per-pound cost, and pounds are the right multiplier. A random-weight pack like Fam Pak Breast Tenders has a per-package cost, and the right multiplier is the number of packs. We multiply by pounds in both cases, which on the second understates the cost and is the shape of a 66.2% margin on chicken.

What would settle it: subs/subs for 20016900000 at storeid 695 (#361) for the week. cost, net_cost, case_size, qty and weight together say which convention those rows follow — and whether there is anything on the row that tells the two kinds apart, which is what decides if this can be fixed in the browser at all.

D

Package deal cannot fire without a count of mixed-price receipts

Backend ask

Package deal is the pattern where the same receipt has the item at two different prices — a BOGO, or a 2-for where one rings full and one discounted. Detecting it needs the number of receipts on which the item rang at more than one price.

The old code got that by downloading every receipt and checking each one. The table comes from the server now, that count is not in it, and the pattern is judged without it — so Package deal never fires. One number on the same query restores it.

Agreed, in phase 5

Categories pairs per category per day, and drops a category-day with no last-week counterpart from both sides. So the percentage’s base is “this week’s sales in the category-days that had a last week” — not the headline. On the original example the header read $100.4K and +7.15%, but the figure compared was about $96.8K against $90.3K. The missing $3.6K is categories that sold this week and did not exist last week.

The header will print that base, so nobody can derive a last-week total the page never used.
