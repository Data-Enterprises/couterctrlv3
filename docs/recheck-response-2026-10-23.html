P and O, settled from the rows

Steve pulled subs/subs for 20016900000 at storeid 695 (#361) for the week. It answers both, and it rules out the cause we proposed — worth saying plainly, because the theory in the last draft was wrong.

The item is priced per pound, and we already cost it per pound. Net sales divided by weight comes to $3.99 on every one of the seven days, which is the shelf price. Per package it would be $7.42, which is not a price anybody set. We had guessed cost and case_size described a package while units were pounds; in fact case_size is 1 and nothing is divided. Our COGS multiplies cost by weight whenever weight is present, so the page is already using the per-pound reading.

ReadingCOGS on the weekMarginImplied cost per lb
Per pound — what we do180.674 lb × $1.35 = $243.9166.1%$1.35
Per package97 packs × $1.35 = $130.9581.8%$0.72

So the 66.2% the run flagged is the real number, on $720.19 of net sales. It is high for chicken, and it is what $3.99 against $1.35 comes to. The other reading needs a $0.72/lb cost on boneless tenders, which is not a chicken price.

What the rows cannot say is which unit cost is in. The price declares itself — avg_unit_price is net sales over weight — and there is no matching field for cost. So the per-pound reading is the consistent one and the plausible one, but only the invoices prove it, and Steve is checking them. If they come back per-package it is a cost-unit problem at the source, not a multiplier to flip here, because nothing on the row tells a true scale item from a random-weight pack.

One thing for the next run: do not read the margin field on subs/subs. It reports about 99% on every row — the server computes it as (total_sales − cost) / total_sales, which is one unit’s cost set against a whole day, on sales that still include tax. It reproduces to seven decimal places on all seven days. Our own interfaces already carry a note not to consume it, and nothing in the live tree does, so this is a warning rather than a fix.

Nothing to change. P and O close here. The margin was right, and the invoices are the only thing that could move it.

D

Package deal cannot fire without a count of mixed-price receipts

Backend ask

Package deal is the pattern where the same receipt has the item at two different prices — a BOGO, or a 2-for where one rings full and one discounted. Detecting it needs the number of receipts on which the item rang at more than one price.

The old code got that by downloading every receipt and checking each one. The table comes from the server now, that count is not in it, and the pattern is judged without it — so Package deal never fires. One number on the same query restores it.

Closed deliberately
